# ADR-0001：以固定上游实现建立完整游玩核心

日期：2026-10-07  
状态：已采纳，0.2.0 已按此实现；验证与发布状态见 [本版记录](../GAMEPLAY-VALIDATION.md)

## 背景

当前版本按预排事件完成 Auto Play，或在无输入模式到期产生 Miss。它能播放谱面，但没有接收操作后判断等级的完整状态机。后续打法算法需要一个能够接受实际输入、复现失误并给出成绩的游玩核心。

MajdataPlay 已有 C# 判定、传感区、Slide 队列和计分实现。AstroDX 曾公开部分 Gameplay 和轨迹代码，可用于对照。重新凭视觉、聊天摘要或少量时间常量拼装规则，会遗漏交互与边界行为。

## 决定

### 上游优先，固定版本

现代 DX 以现有固定 MajdataPlay 提交为主要兼容基准。逐项研究完整调用链；优先复用或做最小适配，保留判定表、状态转移和时间语义，不为风格统一而重写成熟逻辑。

AstroDX 的可用历史源码作为轨迹、Slide 处理和统计的补充对照。来源有冲突时记录差异和选择，以主基准保持内部一致，不能取两者中较宽松的规则拼成第三套。

更新基准时记录新提交与变化，并重跑相关行为测试。源码入口与核验事实只在[研究记录](../../research/upstream-gameplay.md)维护，避免多处抄写。

### 沿用桌面工程，隔离运行环境依赖

保留 C#/.NET、Avalonia 和已有音频/皮肤实现。游玩状态机不依赖 Unity 场景、MonoBehaviour 或 UI 帧率；迁移时只替换实际需要的时间、输入和生命周期适配。无需把整个 Unity 项目或硬件驱动搬入 MaiPlay。

核心流程为“带时间输入 → 区域状态 → 音符状态机 → 判定事件 → 成绩和表现”。采用现有项目和少量直接模块，不预先建立 ECS、规则 DSL、依赖注入平台或插件系统。

### 算法之前先验收规则

先用固定输入日志验证成功和失败，再接入产生这些输入的规划算法。真人设备不是必要条件。区域输入和接触位置映射共用判定器；具体行为由[游玩契约](../specs/gameplay.md)定义。

保留理想 Auto Play 展示用途，允许上游式自动完成；实际输入路径的验收独立进行。不会把 Auto 全 CP 或无输入全 Miss 当成完整判定的证据。

### 按许可复用，保留出处

MajdataPlay 固定版本附 GPL-3.0。复制或改编其代码时保留出处、原版权与适用许可，并按实际复用范围落实对应源码和发布义务；不因原项目说明曾写“独立实现”就排除直接复用。首次引入后同步修改第三方说明，不能继续声称“没有复制源码”。

AstroDX 历史快照的可见性不等于明确复制授权。先检查文件头及适用许可；无明确许可的部分用于行为对照，并从可复用的主基准实现。素材单独核验，不把主仓库代码许可自动套用于皮肤和音效。

这些检查在引入第三方内容的边界完成，不扩散成运行时权限框架或逐文件重复审批。

## 未采用的方案

- 继续只扩充预设 Perfect/Miss 时间线：无法验证实际操作和连带误触。
- 从零重新猜测全部判定：增加与上游偏离的风险，缺少复用收益。
- 整体迁入 Unity：已有播放器、界面和资源管理可继续使用，目前没有足够收益支持重建。
- 先写规划器再修判定器：无法区分算法错误与规则错误，优化结果也不可信。

## 影响

下一阶段工作量以基础机制的行为覆盖为准，不以新增类或设置项数量衡量。实现需要跨解析、播放状态、计分与表现层修改，不能仅增加一个窗口表就宣布完成。

既有发布版本是冻结成果，不直接替换它的说明和二进制。新实现、新验收记录与新发布对应；保留旧验收事实。现有减分达成率复用，随真实最终判定更新。

主界面将常驻设置收进二级页面，具体交互见[界面与设置契约](../specs/player-settings.md)。
